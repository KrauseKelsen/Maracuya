01 / Qué se consiguió

Una base común para mantener la coherencia.

Un token es una decisión de diseño guardada con nombre: un color, una tipografía o una medida. XML y Compose son dos tecnologías que utiliza Android para construir pantallas.

Catálogo centralizado

Colores, tipografías, fuentes e iconos se definen en las bibliotecas compartidas. Ambos tipos de pantalla consumen esa misma base y sus personalizaciones por marca.

Compilación automatizada

Token Exporter transforma el catálogo en recursos para Android durante la compilación. La aplicación recibe la librería preparada, sin ejecutar el exportador.

Componentes con reglas comunes

TextView comparte tokens, variantes, reglas de comportamiento y medidas entre XML y Compose. La estructura sirve de referencia para extender el patrón a otros componentes.

Valor para el equipo: menos lugares donde mantener la misma decisión visual, menor riesgo de diferencias entre pantallas y una base reutilizable para desarrollar nuevos componentes. Son beneficios esperados de la arquitectura; no se han medido tiempos de ahorro.

XML y Compose: problema y objetivos vigentes

Actualizado: 2 de noviembre de 2026. Implementación de referencia: TextView.

El DS define colores, tipografías, fuentes e iconos en las clases Library*. Compose los recibe mediante CompositionLocal; XML necesita recursos Android y un proveedor de tema que funcione fuera de una composición. Mantener dos catálogos produciría diferencias al modificar una marca.

La solución implementada comparte el catálogo, los contratos puros y las decisiones visuales. token-exporter deriva recursos XML durante el build. LibraryThemeSnapshot transporta el tema resuelto a ambos frontends. Las recetas de TokensOverride reciben ese mismo contrato.

Objetivos

  • Modificar cada token en su Library y regenerar sus referencias al compilar.
  • Permitir referencias XML a colores, TextAppearances, fuentes e iconos, además de recetas tipadas.
  • Conservar los valores y comportamientos de Compose como referencia para el TextView nativo.
  • Compartir separación de iconos y tamaño interactivo; diferenciar esas medidas del padding explícito del host.
  • Mantener núcleo, capacidades opcionales y componentes independientes para incorporar nuevos controles.
  • Documentar precedencia, cambios de tema y límites de cada API; comprobarlos con pruebas de recursos, comportamiento y render real.

Alcance actual

wrappers/components/textviews/TextView hereda de AppCompatTextView. Los wrappers de Button, Label y TextField que alojan Compose siguen usando su adaptador de composición; no se han convertido en controles nativos.

El TextView conserva texto y spans, selección, setters Android y drawables relativos. Comparte con Compose tokens, variantes, colores por estado y medidas base. Las diferencias propias de plataforma, como los menús de selección o la presentación de acciones accesibles, se delegan a Android y Compose respectivamente.

La propuesta inicial basada en Label fue sustituida por esta implementación. La arquitectura vigente está en estructura, el manual en TextView, la extensión a otros componentes en responsabilidades y el contrato visual en paridad.

Arquitectura implementada del puente XML–Compose

Actualizado: 2 de noviembre de 2026. Este documento describe código existente.

Fuente y generación

LibraryColorTokens, LibraryTypographyTokens, LibraryIconTokens y el catálogo de fuentes contienen las definiciones. LibraryThemes configura las marcas y sus modos. LibraryThemeSet.resolve entrega un LibraryThemeSnapshot; no se reconstruye una segunda biblioteca en wrappers.

El exportador JVM descubre las propiedades de las Library durante el build y genera colecciones tipadas, roles y aliases de compatibilidad. A continuación exporta recursos Android y referencias Kotlin estáticas. Los escritores de colores, tipografías, iconos, fuentes y estilos opcionales tienen responsabilidades independientes. ExportLibraryTokens conecta estos escritores; agregar un componente que consuma los mismos recursos no exige modificarlo.

CorporateTypography y CorporateIcons son aliases generados para compatibilidad de imports Kotlin. No contienen políticas ni colecciones duplicadas. La API actual utiliza LibraryTypography y LibraryIcons generados en theme.collections.

Flujo en ejecución

LibraryThemes → LibraryThemeSnapshot
  ├─ MyLibraryTheme → CompositionLocal → LibraryTheme.current → componente Compose
  └─ MyLibraryThemeWrp → AndroidThemeResolver → componente nativo

TokensOverrideSource<T> + proveedor de tema
  → ComponentTokenBinding<T> → receta del componente
  → defaults + receta + XML + parche Kotlin
  → adaptación de plataforma → render

El registro conserva recetas, no un tema global ni Views. Cada instancia resuelve el proveedor más cercano. Los wrappers que alojan Compose utilizan wrappers/adapters/compose; el TextView nativo utiliza el resolutor Android.

Distribución de responsabilidades

Ubicación Responsabilidad
core/components/<componente> Tokens, defaults, variantes y políticas compartidas sin Android ni Compose.
tokens/spacings Medidas reutilizables entre componentes, como el objetivo interactivo mínimo.
ui/components/<componente> Lectura de locals, adaptación y render Compose.
wrappers/core Registro, vínculo de tema, fuentes de valores, recursos y gestos de View.
wrappers/capabilities Texto y drawables relativos como capacidades opcionales reutilizables.
wrappers/components/<componente> Lector XML, estado, adaptación, render y callbacks específicos.
token-exporter Descubrimiento y generación durante la compilación; sin responsabilidades de interacción.

Las capacidades no importan componentes concretos. Un Button puede usar texto, iconos y recursos sin depender del TextView del DS. Cada componente conserva su propio registro, variantes y comportamiento.

Configuración declarativa

Los recursos generados se usan con ?attr/libraryColorBrandPrimary, ?attr/libraryTypographyHeadline24 y ?attr/libraryIconAlertsInfo bajo el overlay correspondiente. Las referencias Kotlin están agrupadas en LibraryXmlReferences.

Una receta TextViewTokensOverride permite compartir configuración dinámica entre Compose y XML. XML la selecciona con app:textViewTokensOverride. Los valores nativos específicos se expresan mediante atributos estándar y TextViewNativeOverrides; no se incluyen listeners en tokens.

La precedencia es parche Kotlin > XML/style/TextAppearance resueltos > receta > defaults. Un cambio del proveedor reevalúa recetas. Las referencias ?attr ya resueltas requieren recrear o reinflar con el overlay adecuado para cambiar su tema Android.

Validación y documentación relacionada

Las pruebas verifican límites de dependencias, recursos generados, precedencia, ámbitos, gestos, medidas y línea base. El manual TextView explica la API; escalabilidad explica cómo agregar otro componente; tipografía y colores e iconos explican el catálogo. Paridad documenta el contrato de presentación.

TokenBridgeXML: tema compartido y TextView nativo

Fuente: arquitectura-xml-compose/03-textview-implementado.md

TokenBridgeXML: tema compartido y TextView nativo

La fuente de verdad sigue siendo theme/LibraryThemes.kt, con los tokens atómicos y semánticos existentes. LibraryThemeSet.resolve(...) selecciona el modo y entrega un LibraryThemeSnapshot con colors, typography, fontFamily e icons. El snapshot es un contrato de datos: no vuelve a construir un tema ni mantiene un catálogo paralelo.

Compose conserva sus cuatro CompositionLocal. La fachada LibraryTheme.current los agrupa y respeta también las sustituciones de un local dentro de un scope anidado. XML obtiene el mismo contrato mediante AndroidThemeResolver, que consulta el MyLibraryThemeWrp más cercano. No se abre una composición para resolver un TextView nativo.

Una receta para Compose y XML

La tipografía forma parte de TextViewTokensOverride. No hay un atributo mrcyTypographyToken, una lista de nombres tipográficos propia del componente ni un segundo registro de tipografías.

Definir la receta y registrarla antes de inflar la pantalla, por ejemplo desde Application.onCreate:

import cruxui.android.lib.core.components.textviews.tokens.TextViewTokensOverride
import cruxui.android.lib.theme.LibraryThemeSnapshot
import cruxui.android.lib.wrappers.components.textviews.tokens.TextViewTokensOverrideRegistry

fun sectionTitle(library: LibraryThemeSnapshot) = TextViewTokensOverride(
    typography = library.typography.headline24,
    textColor = library.colors.brandPrimary,
    fontFamily = library.fontFamily,
    iconEnd = library.icons.alerts.info,
)

// Dentro de Application.onCreate(), antes de inflar layouts:
TextViewTokensOverrideRegistry.register("sectionTitle", ::sectionTitle)

La misma función sirve en Compose:

import cruxui.android.lib.theme.LibraryTheme
import cruxui.android.lib.theme.MyLibraryTheme
import cruxui.android.lib.ui.components.textviews.TextView

MyLibraryTheme {
    TextView(
        text = "Información personal",
        tokensOverride = sectionTitle(LibraryTheme.current),
    )
}

Y en XML se selecciona la receta usando el registro existente como patrón:

<cruxui.android.lib.wrappers.theme.MyLibraryThemeWrp
    xmlns:android="http://schemas.android.com/apk/res/android"
    xmlns:app="http://schemas.android.com/apk/res-auto"
    android:layout_width="match_parent"
    android:layout_height="wrap_content"
    app:themeName="Maracuya"
    app:themeStyle="auto">

    <cruxui.android.lib.wrappers.components.textviews.TextView
        android:id="@+id/title"
        android:layout_width="match_parent"
        android:layout_height="wrap_content"
        android:text="@string/section_title"
        app:textViewTokensOverride="sectionTitle"
        app:iconEndContentDescription="@string/more_information" />
</cruxui.android.lib.wrappers.theme.MyLibraryThemeWrp>

section_title y more_information son recursos de la app del ejemplo. El registro almacena funciones puras que reciben la biblioteca activa; no almacena una marca activa global, un Context ni una View. Evitar capturar Activities en esas funciones. Cada instancia evalúa su receta contra su scope al crearse, adjuntarse y actualizar su tema. Los hosts anidados conservan su propio alcance.

Los nombres se normalizan sin depender del idioma del dispositivo. Un nombre desconocido falla con un mensaje explícito; el editor de layouts permite previsualizar con defaults cuando el registro de la app no se ha ejecutado. Reemplazar una receta no observa automáticamente las Views: llamar a refreshTheme() en las instancias existentes. Se mantiene el overload de registro anterior con cuatro argumentos para los otros wrappers.

Las rutas públicas del nuevo TextView Compose siguen disponibles mediante aliases. Ambos frontends usan las mismas clases de tokens, variantes y capacidades de comportamiento. XML no importa LabelTokens ni deriva su contenido de LabelVariant.Optional.

El contrato visual conserva textColor, backgroundColor, errorColor, foregroundColor, disabledColor, iconStart, iconEnd, typography y fontFamily. La tipografía se convierte a tamaño, altura de línea, tracking, peso, cursiva y alineación. HIPERTEXT usa el color de enlace y subrayado; no cambia el texto ni abre enlaces automáticamente. Los iconos son opcionales y siguen el color efectivo del texto, igual que el componente Compose.

Para incorporar otro componente: declarar sus modelos puros en core/components, derivar sus defaults desde LibraryThemeSnapshot, extender TokensOverrideRegistry<SuTokensOverride> y crear su lector, adaptación y renderer nativos. Reutilizar wrappers/core; no copiar el catálogo del tema ni el registro.

<androidx.appcompat.widget.AppCompatTextView
    xmlns:android="http://schemas.android.com/apk/res/android"

La receta registrada es la opción para seguir cambios de tema dinámicos del proveedor. Los recursos ?attr pertenecen al tema Android del Context: cambiar MyLibraryThemeWrp.themeStyle actualiza recetas y tokens semánticos, pero no reinfla estilos Android ni cambia el Context de Views existentes. Para cambiar referencias XML explícitas de marca/modo, aplicar el overlay correspondiente y recrear o reinflar la pantalla. Mantener themeName/themeStyle y el overlay coherentes cuando se combinan ambos mecanismos.

La salida vive en maracuya/build/generated/libraryTokens/ y no se edita ni versiona. No hay reflexión ni búsqueda de recursos por nombre durante el render; el generador produce enlaces estáticos a R. La reflexión se limita al proceso de construcción y a pruebas de paridad del catálogo. Ver el módulo exportador para agregar temas o assets.

Setters, precedencia y comportamiento

import cruxui.android.lib.wrappers.components.textviews.TextView as DesignTextView
import cruxui.android.lib.wrappers.components.textviews.behavior.TextViewBehavior
import cruxui.android.lib.wrappers.components.textviews.variant.TextViewVariant

val title = findViewById<DesignTextView>(R.id.title)
title.text = "Datos de contacto"       // setText nativo: conserva spans
title.setVariant(TextViewVariant.HIPERTEXT)
title.setColor(title.getThemeTokens().colors.brandPrimary)
title.setTypography(title.getThemeTokens().typography.headline24)
title.setTextSizeSp(26f)
title.setOnClickListener { /* acción del texto */ }
title.setOnDoubleClickListener { /* doble pulsación del texto */ }
title.setOnLongClickListener { /* pulsación larga */ true }
title.setOnIconEndClickListener { /* acción independiente del icono */ }
title.setOnIconEndLongClickListener { /* ayuda */ true }
title.setBehavior(TextViewBehavior.Selectable)

Se mantienen las APIs nativas de texto, spans, maxLines, ellipsize, tamaño, fuente, ColorStateList, espaciado, fondos, alineación y selección. Los setters de estilo gestionados se conservan al refrescar el tema o cambiar de variante. setError y setErrorState comparten estado; deshabilitar bloquea acciones del texto e iconos. La selección nativa reserva long press y doble pulsación del texto; al desactivarla se recuperan los callbacks configurados. Las acciones de iconos se exponen también a accesibilidad. Cada icono interactivo reserva una celda mínima de 48dp y conserva el asset centrado; cada icono presente se separa 8dp del texto. Ambos valores proceden de TextViewLayoutTokens, compartido con Compose. Un icono decorativo ocupa solamente su tamaño.

Prioridad: parche de ejecución > XML resuelto por Android > receta registrada > defaults de la variante en el tema. Dentro de una capa, valores nativos específicos como tamaño pueden ajustar una tipografía completa. Aplicar después una tipografía sustituye sus métricas anteriores; aplicar después setTextSize ajusta solo el tamaño. La familia es un campo independiente. lineHeight y lineSpacing son alternativas; el último setter elige una.

setTokensOverride usa el mismo contrato semántico que Compose. Su textColor cambia el estado normal; errorColor y disabledColor mantienen la política compartida. setTextColor nativo aplica su color o selector a todos los estados. setNativeOverrides(TextViewNativeOverrides(...)) acepta representaciones Android como recursos, dimensiones, selectores, drawables o Typeface cuando sean necesarias. setColor(Int) espera @ColorRes; para un ARGB usar setTextColor(Int).

Los parches combinan campos presentes; null significa ausencia. Para retirar un icono usar setIconStart(null as IconToken?), setIconEnd(null as IconToken?) o ViewIcon.None en el parche nativo. clearOverrides, clearColorOverride y clearTypographyOverrides restauran los valores inferiores de XML/receta. setTokensOverrideName(null) retira la receta. setThemeTokens(snapshot) permite inyección explícita por instancia; null restaura la herencia del proveedor.

Migración y validación

  • El wrapper anterior basado en Label se sustituye por el nuevo contrato TextView. optional, setTokens, setComponentTokensOverride, clearTextOverride y los atributos particulares typography/textColorRole de aquella propuesta se retiran. El componente Label conserva su implementación independiente.
  • La configuración semántica va a TextViewTokensOverride; recursos/valores exclusivamente Android van a TextViewNativeOverrides. Las variantes Kotlin son DEFAULT y HIPERTEXT; en XML, standard y hipertext.
  • Los iconos incluidos usan resourceName para mantener puro el catálogo. Para obtener un drawable ID en código Android usar LibraryAssetResources.icon(token); no leer filledResId de un icono incluido, pues ahora es cero. Se conserva IconToken(name, filledResId = R.drawable.mi_icono) para recursos de la app.
  • Los adaptadores Compose y Views consumen el mismo catálogo físico completo de fuentes, incluidos peso 900 y cursivas.

Las pruebas cubren catálogo exportado claro/oscuro, 28 tipografías, enlaces de iconos y fuentes, recetas, scopes, inflación, precedencia, fuentes, alineación con/sin RTL, estados, selección, gestos y accesibilidad. Ejecutar:

./gradlew :maracuya:testDebugUnitTest :maracuya:lintDebug :app:assembleDebug :maracuya:assembleDebugAndroidTest

Las pruebas instrumentadas de interacción Compose requieren un dispositivo/emulador con :maracuya:connectedDebugAndroidTest. Compilar su APK no equivale a ejecutarlas. La revisión visual en dispositivo es adicional a las verificaciones automatizadas. Los callbacks y parches de ejecución se reaplican desde el propietario de la pantalla al recrearla; no se serializan snapshots ni listeners.

La galería y el contrato de medidas se detallan en paridad Compose–XML.

Componentes XML independientes y responsabilidades compartidas

El catálogo de theme/LibraryThemes sigue siendo la fuente del DS. La exportación a recursos Android y la resolución de recetas durante la ejecución son procesos separados. Un componente nuevo no debe modificar un registro global, agregar condiciones por tipo en el núcleo ni depender del TextView del DS.

wrappers/components/<componente> Definir atributos, variantes, tokens, comportamiento y coordinación propios Internos de otro componente

Los archivos históricos de core/behavior/CompoundDrawableBehaviorController conservan una fachada de compatibilidad Kotlin/Java. La implementación opcional está en capabilities/compounddrawables. AndroidTokenAdapter también conserva su API y delega a cargadores separados. Los nombres públicos TextColor, TextFont y TextDimension se conservan: describen fuentes reutilizables, no una dependencia de la clase TextView del DS. Sus modelos ya no cargan recursos.

Decisiones SOLID

  • Responsabilidad única: los lectores decodifican; los resolutores convierten; los renderizadores escriben; behavior controla interacciones. El punto de entrada del exportador solo coordina.
  • Abierto a extensión: cada CatalogWriter produce su propia salida. Una adaptación opcional no modifica los escritores generales. Cada componente declara su registro con su tipo de override.
  • Sustitución: cualquier TokensOverrideSource<T> que cumpla consulta/resolución puede alimentar el vínculo; cualquier ExportOutput puede recibir la misma exportación. Las pruebas usan salida en memoria.
  • Segregación: los consumidores de recetas reciben un contrato de lectura, no operaciones de registro/borrado. Un componente sin texto no incorpora la capacidad tipográfica ni sus atributos.
  • Inversión de dependencias: ComponentTokenBinding<T> recibe la fuente de recetas y una función que obtiene el tema heredado. No consulta una View ni un CompositionLocal. El adaptador de cada plataforma aporta esos datos.

No se añadió una superclase que imponga texto, iconos, error, selección y eventos a todos los componentes. Cada uno compone sus capacidades. Esto evita una jerarquía central con decenas de opciones irrelevantes.

Incorporar otro componente

Una estructura de componente nativo mantiene el mismo patrón del TextView:

components/buttons/
  Button.kt                 # API nativa, setters y ciclo de vida
  attributes/               # Styleable propio y decodificación
  core/                     # Estado exclusivo del Button
  tokens/                   # Override, registro y resolución de capas
  tokensrender/             # Valores Android para ese Button
  render/                   # Aplicación de valores a su View
  variant/                  # Variantes visuales del Button
  behavior/                 # Capacidades y reglas de interacción propias
  1. Definir tokens, defaults y variantes semánticos independientes del frontend. Cuando existe una implementación Compose, sus defaults deben compartirse con el adaptador nativo, como ocurre con el núcleo actual del TextView.
  2. Declarar un registro TokensOverrideRegistry<ButtonTokensOverride>. El mismo nombre de receta puede existir en otros registros; sus tipos y almacenamiento permanecen separados.
  3. En una View nativa usar ComponentTokenBinding con ese registro y un proveedor de tema. Releer el ámbito al adjuntarse/cambiar configuración y al recibir refreshTheme. Cambiar una receta no notifica automáticamente.
  4. Si el componente tiene texto, componer NativeTextStyleOverrides; declarar sus propios índices mediante TextAttributeIndices y usar el lector, resolutor y renderer tipográfico. No copiar TextViewAttributeReader. El modelo público NativeTextStyleOverrides permite exponer una propiedad textStyle en nuevos overrides. El TextView conserva sus campos planos públicos mediante adaptación para no romper consumidores existentes.
  5. Mantener colores de estado, precedencia específica, variantes y behavior en el componente. No todo componente tiene error, selección, dos iconos o el mismo orden de estados. Los helpers compartidos no imponen esas decisiones.
  6. Incorporar gestos, superficies o drawables relativos solo cuando corresponda. ViewGestureController recibe una política active; la selección del texto se decide en el behavior de TextView.
  7. Para un wrapper que aloja Compose, conservar MrcyXmlComposeView y resolver recetas mediante resolveInComposition. Ese adaptador lee LibraryTheme.current; el registro sigue siendo independiente.

ButtonWrp existente conserva el render Compose. Sus recetas ya pasan por el adaptador común, al igual que las recetas de navegación, Label y TextField. Esta refactorización no lo convierte en un Button nativo ni migra los 63 componentes por anticipado. Establece capacidades y contratos reutilizables para implementarlos sin depender entre sí.

Consumo existente de Button desde XML

Registrar antes de inflar, por ejemplo dentro de Application.onCreate:

ButtonTokensOverrideRegistry.register("accionPrincipal") { library: LibraryThemeSnapshot ->
    ButtonTokensOverride(
        contentColor = library.colors.fgDefault,
        textTypography = library.typography.headline24,

}

Dentro de un MyLibraryThemeWrp y un layout que declare los namespaces Android y app:

<cruxui.android.lib.wrappers.components.buttons.simple.ButtonWrp
    android:layout_width="match_parent"
    android:layout_height="wrap_content"
    app:text="Continuar"
    app:buttonTokensOverride="accionPrincipal" />

Este consumo no necesita nuevas variables en token-exporter ni utiliza tokens de TextView. La receta puede ser una función compartida con el consumidor Compose, que le pasa LibraryTheme.current.

Límites y verificación

El exportador trabaja con temas conocidos al construir; las recetas también admiten bibliotecas configuradas en ejecución. Cambiar una biblioteca no crea nuevos IDs Android ni sustituye el Context de una View.

Las pruebas cubren recursos y estilos, cambios de ámbito, independencia de registros de tipos diferentes, render tipográfico sobre android.widget.Button, gestos sobre una View sin texto y regresiones del TextView. Las reglas de dependencias impiden importar componentes concretos desde núcleo, capacidades o adaptadores.

Las medidas comunes de TextView viven en core/components/textviews/tokens/TextViewLayoutTokens; el mínimo interactivo reutilizable vive en tokens/spacings/InteractionSpacings. Ver paridad de render para la adaptación de iconos nativos sin alterar los defaults Compose.

Consumo desde Compose

Agregar o modificar un estilo

Modificar exclusivamente LibraryTypographyTokens. Ejemplo de una propiedad nueva:

/** Encabezado de campaña compartido por los consumidores del DS. */
val campaignTitle = TypographyToken(
    fontSize = FontSizeTokens.s24,
    lineHeight = LineHeightTokens.lineHeightFrom(FontSizeTokens.s24, LineHeightTokens.ShortRatio),
    weight = FontWeightTokens.Bold,
)

Tras compilar aparecen automáticamente:

  • library.typography.campaignTitle y library.typography.copy(campaignTitle = ...).
  • TextTypographyRole.CampaignTitle.
  • ?attr/libraryTypographyCampaignTitle.
  • @style/TextAppearance.Maracuya.CampaignTitle y sus dimensiones.
  • ThemeExports.xmlReferences.typography.campaignTitle.

El ejemplo no incorpora ese estilo ficticio al catálogo. No editar enums, resolutores, escritores ni la tabla histórica de compatibilidad. Renombrar o eliminar una propiedad cambia la API pública de esa tipografía.

Para cursivas declarar italic = true: ese campo es el contrato que usan ambos adaptadores. style es un campo histórico y no sustituye el peso ni el booleano de cursiva. Los estilos de cursiva existentes ya lo declaran. La familia tipográfica continúa perteneciendo al tema, separada de las métricas de cada estilo.

Generación y responsabilidades

  1. catalogSchema compila los catálogos Library de colores, tipografías e iconos y sus tipos base.
  2. generateCatalogApi descubre los nombres y genera LibraryTypography y TextTypographyRole.
  3. El exportador completo compila esa API, resuelve LibraryThemes y obtiene las métricas efectivas con asMap.
  4. Los escritores existentes generan atributos, recursos y enlaces; CatalogApiWriter entrega también las fuentes semánticas y de roles a Android.
  5. Compose y Views consumen el mismo tema; ninguna View usa reflexión para resolver un rol.

Las pruebas recorren todas las propiedades del objeto Library, comprueban los recursos y las conversiones Compose/nativas, inflan el ejemplo XML y verifican que un nombre nuevo se incorpora sin editar otras tablas.

La generación se comparte ahora con colores e iconos. TextTypographyRole es un alias de LibraryTypographyRole; CorporateTypography es un alias de compatibilidad para theme.collections.LibraryTypography. Consultar la estructura común actual.

Los valores se mantienen en Library. El build genera las proyecciones necesarias para los temas, Kotlin y XML. Un nuevo componente consume estas proyecciones; no necesita añadir sus tokens al exportador ni al core de wrappers.

Qué responsabilidad conserva Corporate

Ninguna responsabilidad de ejecución. CorporateIcons y CorporateTypography son aliases generados que permiten recompilar imports Kotlin existentes. El DS utiliza theme.collections.LibraryIcons y LibraryTypography directamente.

La colección tipográfica permite crear instancias y usar copy sobre los defaults del objeto LibraryTypographyTokens. La colección de iconos solo agrupa referencias a las categorías originales; ya no copia cientos de propiedades a GeneralIcons, AlertsIcons, etc. Los colores usan directamente LibraryColorTokens, que ya es una colección configurable.

semantics no contiene clases manuales ni valores. Los aliases podrían retirarse en una migración que actualice los imports de los consumidores. Los antiguos tipos tokens.icons también son aliases de sus categorías Library. Esto conserva compatibilidad de fuentes Kotlin habitual, no compatibilidad binaria/Java con una versión anterior publicada: hay que recompilar los hosts.

Se conservan los accesos y recursos históricos people.accesibleMenu y extension.lgDavibankHouseEmpty como propiedades calculadas sobre accessibleMenu y davibankHouseEmpty. Los argumentos nombrados de constructor/copy usan ahora estos últimos nombres Library; no existe un segundo campo con otro valor.

atoms/LibraryTypographyTokens ──► LibraryTypography generada

atoms/LibraryIconTokens       ──► LibraryIcons generada (referencias a los grupos)
               │
               ▼
      LibraryThemeSet / LibraryThemeSnapshot

Las tareas se encadenan con la compilación normal. Un cambio en los catálogos invalida sus entradas, regenera las proyecciones y compila Android. Si se elimina una propiedad se retiran sus recursos generados; los consumidores de ese nombre deben migrarse. El host del AAR no ejecuta token-exporter ni necesita reflexión en la app.

Recetas y personalización en ejecución

Registrar antes de inflar el layout:

TextViewTokensOverrideRegistry.register("information") { library: LibraryThemeSnapshot ->
    TextViewTokensOverride(
        typography = library.typography.body1,
        textColor = library.colors.linkDefault,
        iconStart = library.icons.alerts.info,
    )
}

El XML selecciona app:textViewTokensOverride="information". La función recibe el tema del ámbito de la View; no debe capturar un snapshot global ni leer CompositionLocals. La misma función de receta puede utilizarse en Compose pasándole LibraryTheme.current.

Para setters nativos:

view.setColorRole(LibraryColorRole.InfoText)
view.setIconStart(ViewIcon.Role(LibraryIconRole.AlertsInfo))
view.setTypography(LibraryTypographyRole.Headline24)

TextColorRole y TextTypographyRole siguen disponibles como aliases. Las selecciones Semantic { ... } también siguen funcionando. Los roles se evalúan al resolver la View y se actualizan al proporcionar otro snapshot. Pasar un ColorToken o IconToken fijo expresa una sustitución fija.

Una marca se personaliza con las mismas colecciones:

val base = LibraryThemes.Maracuya
val custom = base.copy(
    lightTokens = base.lightTokens.copy(brandPrimary = ColorToken(0xff123456)),
    iconAtoms = base.iconAtoms.copy(
        alertsIconsLibrary = base.iconAtoms.alertsIconsLibrary.copy(
            info = base.iconAtoms.alertsIconsLibrary.warning.copy(iconSize = 24),
        ),
    ),
)

MyLibraryTheme(theme = custom) aplica el tema en Compose. view.setThemeTokens(custom.resolve(false)) lo aplica a esa View. Para exportarlo permanentemente como XML, declararlo en LibraryThemes.all y recompilar. Los cambios en ejecución no reescriben recursos compilados ni reinflan XML automáticamente.

Cómo ampliar el catálogo

  1. Color: agregar una propiedad ColorToken en LibraryColorTokens y definir sus valores por modo en cada paleta construida explícitamente.
  2. Icono: agregar la propiedad IconToken y su valor base en su clase atoms/icons/Library*. resourceName debe existir en res/drawable; el catálogo exportable no debe usar IDs del host.
  3. Grupo: agregar su propiedad y default en LibraryIconTokens, con @get:LibraryIconGroup("nombre"). No se modifica ningún registro del exportador.
  4. Compilar. Aparecen roles, consultas, atributos, enlaces de tema y referencias Kotlin.

Modificar un token existente propaga sus valores base al recompilar. Las sustituciones explícitas de una marca siguen prevaleciendo. No modificar clases generadas, resolutores de wrappers ni listas de roles. Una tipografía nueva conserva el mismo procedimiento descrito en la guía tipográfica.

Escalar a otros componentes

Un Button puede recibir el mismo LibraryThemeSnapshot, usar un TokensOverrideRegistry<ButtonTokensOverride> propio y seleccionar library.colors, library.typography e library.icons. El catálogo no incorpora comportamiento, variantes ni callbacks. ViewIcon y TextColor describen fuentes; los resolutores seleccionan tokens; los adaptadores cargan recursos; cada componente mantiene sus reglas visuales y de interacción.

La exportación de estos recursos funciona sin TextWidgetStyleWriter. Crear más componentes no añade casos a LibraryIconsSource, ColorCatalogSource, CatalogApiWriter ni a los resolutores de roles.

Paridad del TextView Compose y XML

Actualizado: 3 de noviembre de 2026. Compose es la referencia de presentación del DS.

Contrato compartido

Aspecto Default de ambos frontends
Tipografía y fuente library.typography.label y familia del tema activo.
Color fgDefault; HIPERTEXT utiliza linkDefault y subrayado.
Estados Deshabilitado prevalece sobre error, y error sobre normal. Los iconos siguen el color del texto.
Superficies Fondo y foreground transparentes.
Iconos Ausentes hasta configurarlos; error no agrega un icono implícito.
Separación 8dp entre el texto y cada icono presente.
Icono decorativo Ocupa IconToken.iconSize.
Icono con acciones Celda mínima de 48 × 48dp, con el asset centrado y sin escalarlo.
Disabled Conserva las celdas y desactiva acciones.
Padding exterior No se añade padding al componente; el host puede configurarlo.
Fuente includeFontPadding=false.
Líneas Mínimo 1, máximo sin límite práctico salvo configuración explícita.

core/components/textviews/tokens/TextViewLayoutTokens contiene las medidas comunes. tokens/spacings/InteractionSpacings aporta el tamaño interactivo global, reutilizable por otros componentes. No se mantienen archivos TextViewDefaults distintos en cada frontend.

Compose conserva su fila, iconos opcionales y texto con weight(fill=false) cuando hay iconos. XML conserva AppCompatTextView, con sus APIs de texto y selección. Las capacidades nativas adaptan la disposición:

  • AndroidIconLoader utiliza FittedIconDrawable para conservar la proporción del asset, como ContentScale.Fit en Compose. El decorador expone el tamaño intrínseco cuadrado del token y recalcula el centrado cuando Android o el editor XML cambian sus límites; no utiliza márgenes fijos que puedan deformar iconos rectangulares.
  • CompoundDrawableRenderer centra el asset dentro de la celda solicitada y aplica tintes.
  • InlineCompoundDrawableLayout mide el ancho intrínseco del texto y reserva el sobrante al final del contenido; no cambia android:padding del host.
  • OffsetCompoundDrawable coloca el icono final junto al texto, incluso con match_parent.
  • CompoundDrawableGeometry utiliza ese mismo desplazamiento para las acciones en LTR y RTL.
  • NativeTextTouchTarget restringe el inicio del gesto al bloque de texto con el mínimo táctil, después de atender las acciones de iconos.

Estas capacidades no conocen el tema, registro, variantes ni clases concretas del DS. Un componente nuevo las incorpora cuando necesita ese tipo de disposición.

Uso XML

<cruxui.android.lib.wrappers.components.textviews.TextView
    xmlns:android="http://schemas.android.com/apk/res/android"
    xmlns:app="http://schemas.android.com/apk/res-auto"
    android:id="@+id/information"
    android:theme="@style/ThemeOverlay.Maracuya"
    android:layout_width="match_parent"
    android:layout_height="wrap_content"
    android:text="@string/information"
    app:iconEnd="?attr/libraryIconAlertsInfo"
    app:iconEndContentDescription="@string/show_information" />

El host declara y traduce information y show_information. Sin callback, el icono es decorativo. Para hacerlo interactivo:

val view = findViewById<cruxui.android.lib.wrappers.components.textviews.TextView>(R.id.information)
view.setOnIconEndClickListener { showInformation() }

El callback reserva la celda mínima. La descripción localizada debe existir antes de medir un icono interactivo, igual que en Compose. Quitar el último callback restaura el tamaño decorativo; retirar el icono elimina también su separación. Deshabilitar conserva la disposición.

app:iconPadding, android:drawablePadding y setCompoundDrawablePadding(px) permiten una separación explícita. android:padding, includeFontPadding, minLines, maxLines, ellipsize y los setters Android mantienen sus opciones. Esas personalizaciones pueden producir una apariencia distinta del default y deben aplicarse de manera equivalente al comparar frontends.

Los gestos de texto e iconos son independientes. Selección reserva pulsación larga y doble toque del texto; sus callbacks se conservan al desactivar la selección. Los iconos siguen disponibles. El espacio libre fuera de las zonas táctiles no activa el texto. Los menús de selección y la representación de acciones accesibles pertenecen a cada plataforma y no se fuerzan a ser visualmente idénticos.

Para RTL, el host habilita android:supportsRtl="true" en su <application>. Android necesita esa declaración para aplicar layoutDirection a las Views. El manifiesto del APK de pruebas también la declara; LocalLayoutDirection de Compose por sí solo no habilita RTL en una aplicación Android.

Exportación de los catálogos Library

token-exporter es una herramienta JVM de construcción. Compila las definiciones puras de Library y genera las APIs y los recursos compartidos por Android. No se incluye como dependencia de ejecución del AAR. El host que consume el AAR recibe clases y recursos ya compilados.

Una fuente por familia

Familia Fuente editable Proyección generada
Tipografía atoms/LibraryTypographyTokens LibraryTypography, roles, dimensiones y TextAppearance
Colores atoms/LibraryColorTokens y sus paletas Consultas sobre la misma colección, roles, colores y atributos
Iconos atoms/LibraryIconTokens y atoms/icons/Library* LibraryIcons con referencias a los grupos originales, roles y atributos de asset/tamaño/tinte
Fuentes físicas theme/FontAssetCatalog Familias XML y enlaces estáticos a recursos

theme.collections contiene las colecciones generadas LibraryTypography y LibraryIcons. Los colores usan directamente LibraryColorTokens, que ya admite personalización con copy. theme.catalog contiene las consultas y los roles de las tres familias.

semantics ya no tiene implementaciones manuales. CorporateTypography y CorporateIcons se generan como aliases Kotlin de compatibilidad. Los antiguos tipos tokens.icons.* también son aliases de las categorías Library; sus funciones get*Icons devuelven esas mismas instancias. No hay una segunda lista de iconos ni otra fuente de valores.

Flujo automático de Gradle

  1. catalogSchema compila los catálogos Library y sus tipos puros, sin temas ni APIs generadas.
  2. generateCatalogApi descubre los getters y genera colecciones, consultas, roles y aliases en token-exporter/build/generated/catalogApi.
  3. Se compila el exportador completo con esas fuentes. ThemeCatalogReader consulta los temas efectivos mediante sus asMap; no utiliza reflexión.
  4. :maracuya:generateLibraryTokens produce recursos y código bajo maracuya/build/generated/libraryTokens. CatalogApiWriter transporta las mismas fuentes a Android mediante un manifiesto generado.
  5. Android compila esas fuentes y recursos junto al DS. La app consume el AAR normalmente.

Las dos tareas conocen sus salidas y su classpath. Modificar un valor o una propiedad de Library invalida la generación; no es necesario ejecutar una tarea extra. Ambas limpian exclusivamente sus directorios generados cuando vuelven a ejecutarse para retirar salidas obsoletas. Una compilación limpia también reconstruye todo.

La reflexión se utiliza solo en catalogSchema. Los componentes reciben consultas Kotlin directas y bindings estáticos a R, sin reflexión, getIdentifier ni exportación durante el render.

Agregar o modificar tokens

  • Tipografía: declarar un val TypographyToken en LibraryTypographyTokens.
  • Color: declarar un val ColorToken en LibraryColorTokens y definir sus valores en las paletas claras/oscuras construidas explícitamente.
  • Icono: declarar un val IconToken en su categoría Library y asignar su valor en el catálogo base. resourceName apunta a un archivo de res/drawable sin extensión.
  • Categoría de iconos: declarar la propiedad en LibraryIconTokens, anotar su getter con @get:LibraryIconGroup("nombrePublico") y configurarla en Default. No agregar una lista al exportador. legacyType solo se utiliza para los aliases anteriores.
  • Marca: declarar un LibraryThemeSet y añadirlo a LibraryThemes.all. Sus valores efectivos generan sus overlays; cambiar el catálogo base no sobrescribe una personalización explícita de marca.

Después, compilar el módulo o la app. No modificar enums, resolutores, referencias XML ni archivos de build/generated. Las listas legacyOrder conservan posiciones históricas; no son listas de tokens admitidos y no deben ampliarse.

Los nombres exportados son API pública. Renombrar o eliminar una propiedad elimina su recurso en la siguiente generación. Para conservar una lectura anterior puede añadirse una propiedad calculada que devuelva el token actual. Así se conservan people.accesibleMenu y extension.lgDavibankHouseEmpty, junto a los nombres Library corregidos.

Recursos y consumo

El build genera libraryColorNombre, libraryTypographyNombre, libraryIconGrupoNombre, libraryIconGrupoNombreSize y libraryIconGrupoNombreTint. El tinte null se representa como @null; no inventa un color. Asset, tamaño y tinte son referencias independientes para que cada componente aplique su política.

LibraryXmlReferences agrupa las referencias en colors, typography, lineHeight, fonts, icons, iconSizes e iconTints. Cada hoja es un ID de atributo, no un color, dimensión o drawable ya resuelto. ThemeExports.xmlReferences expone el mismo objeto.

Un ThemeOverlay conecta los atributos con los valores de marca y modo. Los snapshots creados mediante copy durante la ejecución siguen funcionando con Compose y las recetas/roles de Views, pero no crean IDs ni reescriben los recursos XML compilados. Un icono exclusivo del host con filledResId también pertenece a la ejecución; el catálogo exportable necesita un resourceName empaquetado en el DS.

Responsabilidades y extensión

  • src/catalogSchema: descubrimiento, escritores por familia, compatibilidad y composición de las APIs.
  • catalog: modelo de exportación y adaptación de los temas efectivos.
  • validation: compatibilidad de roles, nombres y presencia de assets.
  • android: escritores independientes de atributos, colores, TextAppearance, fuentes y overlays.
  • kotlin: transporte de APIs, bindings estáticos y referencias de atributos.
  • components/text: adaptación opcional para estilos de widgets con texto.
  • output: escritura y nombres de recursos; permite probar salidas en memoria.

ExportLibraryTokens.kt solo compone lectores, validación y escritores. Agregar un Button u otro componente que use estas familias no requiere editar el exportador. Su comportamiento y registro pertenecen al componente. Solo una nueva clase de recursos estáticos derivados necesita un escritor adicional.

Compatibilidad y validación

Los aliases conservan imports de fuentes Kotlin, no la identidad de clases JVM de una versión publicada. Los hosts deben recompilarse; código Java o binarios que dependan de las clases anteriores necesitan migración. Para argumentos nombrados de constructores/copy de los dos iconos renombrados usar accessibleMenu y davibankHouseEmpty; los accesos de lectura y recursos anteriores se mantienen.

Las pruebas recorren los catálogos completos, comprueban personalizaciones, identidad de categorías, paridad de recursos y resolutores, exportación sin widgets y ausencia de assets. La guía de colores e iconos contiene ejemplos de Compose, registros y XML.
